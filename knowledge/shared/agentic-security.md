## What Agentic Security Is

Agentic security is the security discipline that addresses systems where an LLM is **not the endpoint of inference** but the **driver of multi-step action** — calling tools, spawning sub-agents, persisting state, and producing side effects on external systems. The threat surface is fundamentally different from LLM-as-chat. In LLM-as-chat the worst plausible failure is bad output. In an agent system the worst plausible failure is bad output that **autonomously triggers wire transfers, data exfiltration, customer-facing communications, or further agent invocations**, each compounding blast radius before any human review.

2026 is the inflection point because two forcing functions converged. First, NIST's Feb 2026 CAISI red-team release reported that novel attack techniques targeting AI agents achieved an **81% task-hijacking success rate** in their test corpus, versus **11% for the strongest known baseline attacks** against the same agent systems — the gap reflects agent-specific attack techniques, not a single-turn-chat-vs-agent comparison. Second, MITRE ATLAS v5.4 (Feb 2026) added agent-specific techniques — including Memory Poisoning and AI-agent tool-invocation/tool-poisoning techniques — that did not exist in the pre-agent taxonomy, formalizing the recognition that an autonomous agent's plan, tools, memory, and peer relationships are each a distinct adversarial surface.

This pack is the V2V product-org reference for the security architecture team's conversations with the rest of the org. It is **not** a substitute for an engagement with qualified security engineers, a regulatory readiness audit, or counsel review of incident-disclosure obligations. It is drafting-and-triage scaffolding to help the security architect produce a structured first pass that a qualified human then reviews, validates, and owns.

## The Agent Threat Surface — A First-Principles Decomposition

Before mapping to any external taxonomy, V2V decomposes an agent system into the five surfaces where adversaries act. Every defensive control in this pack attaches to one of these surfaces; the value of the decomposition is that it is exhaustive over what an agent can *do*, so no threat hides between named list items.

1. **Perception** — the agent reads untrusted content (web pages, emails, documents, tool outputs, PR/issue text, skill metadata). Adversaries plant instructions in data the agent treats as trusted.
2. **Planning** — the agent decides what to do next, often re-planning on tool output. Adversaries steer the agent toward an objective the principal never requested.
3. **Action** — the agent invokes tools with side effects. Adversaries cause the wrong tool, wrong arguments, or wrong target — turning the agent's own capabilities into the attack.
4. **Memory** — the agent persists and retrieves state (vector stores, conversation logs, context caches). Adversaries corrupt what the agent will later believe.
5. **Delegation** — the agent spawns or calls peer agents. Adversaries impersonate one agent to another, or escalate across the boundary.

The defining property of an agent system is that a failure at any one surface **propagates into action** at the others. A perception-layer injection becomes a planning-layer goal change, becomes an action-layer side effect, becomes a memory-layer corruption that re-injects on the next run. Bounding blast radius means assuming a failure at each surface and constraining what it can reach downstream — which is what the identity-and-capability layer (Q2-3.1) plus runtime monitoring provide.

## Threat Model — MITRE ATLAS v5.4 Agent Techniques

MITRE ATLAS v5.4 (Feb 2026; 16 tactics, 84 techniques) adds explicitly agent-targeted techniques to the existing AI/ML adversarial taxonomy. The techniques most load-bearing for product-org architectures running agent systems in 2026, mapped to the five-surface decomposition above:

| ATLAS Technique | Surface | What It Is | Architectural Surface & Mitigation |
|---|---|---|---|
| **AML.T0051 (LLM Prompt Injection)** | Perception | Adversary embeds attacker-controlled instructions in agent-reachable data (web pages, emails, documents, tool outputs). Exists in ATLAS, but agent-system blast radius differs from chat because the injected instruction can drive action, not just output. | Any tool that returns adversary-controllable content (web fetch, email read, document fetch). Mitigation: structured tool output, instruction-data separation, runtime monitoring for plan deviation. |
| **Goal Manipulation** *(MITRE ATLAS v5.4 agent tactic — refer by name; confirm current ID at atlas.mitre.org)* | Planning | Adversary causes the agent to pursue an objective different from the one the principal requested, often via injection chains across tool boundaries. | Multi-step agent workflows; any agent that re-plans based on tool output. Mitigation: principal-bound goal verification at each plan step, plan-vs-action audit. |
| **AML.T0053 (AI Agent Tool Invocation)** / **AML.T0110 (AI Agent Tool Poisoning)** | Action | Adversary causes the agent to invoke tools in ways the principal did not authorize — wrong tool, wrong arguments, wrong target — or modifies the tools themselves so future invocations execute attacker-controlled behavior. | Tool-router architectures; any agent with write or external-action capabilities. Mitigation: capability tokens scoped per-action (Q2-3.1 §Capability Tokens), per-action approval gates for high-impact tools, tool-integrity verification. |
| **Masquerading (AML.T0074)** *(applied here as inter-agent spoofing — impersonation across the agent boundary)* | Delegation | Adversary impersonates one agent to another, escalating privilege or exfiltrating data across agent boundaries. | Any multi-agent architecture. Mitigation: see §Agent-to-Agent Threat Model below — anchored on Q2-3.1's four identity patterns. |
| **AML.T0080 (Memory Poisoning)** | Memory | Adversary corrupts the agent's persistent memory store (vector DB, conversation log, retrieved-context cache) so subsequent runs are misdirected. | RAG architectures; agents with long-running memory. Mitigation: provenance-tracked memory writes, memory-source isolation, retrieval-side filtering (see §Retrieval & Memory Corruption below). |

Per B-M4: ATLAS technique IDs cited above (`AML.T0051`, `AML.T0053`, `AML.T0074`, `AML.T0080`, `AML.T0110`) are verified real identifiers in ATLAS v5.4. Goal Manipulation is referred to by **tactic name only** with no invented identifier; ATLAS technique IDs are assigned at publication time and the agent-specific block continues to be canonicalized — consult atlas.mitre.org for the current authoritative numbering before citing a specific ID downstream. In particular, agent tool-poisoning is split in v5.4 between `AML.T0110` (AI Agent Tool Poisoning) and the `AML.T0011.002` (Poisoned AI Agent Tool) sub-technique; confirm which applies before citing it downstream.

**V2V architecture review gate mapping**: each technique above maps to a specific gate in the V2V architecture review process. Goal Manipulation and Tool-Use techniques are blocking findings at the Architecture Review Gate (pre-build); Inter-Agent Spoofing is a blocking finding at the Integration Review Gate (pre-cross-agent-deployment); Memory Poisoning is a blocking finding at the Data Architecture Review Gate (pre-RAG-deployment); Prompt Injection is a continuous-control finding at the Operational Readiness Gate.

## Threat Model — Seven Agent-Specific Failure Modes (V2V First-Principles)

The five-surface decomposition surfaces seven recurring failure modes that V2V treats as first-class review items. These are authored here as V2V product-org guidance organized around the agent's own behavior; each names the surface it attacks and the defensive control that bounds it.

| Failure Mode | Surface | What Goes Wrong | Agent-Lens Risk & Mitigation |
|---|---|---|---|
| **Injection-into-action** | Perception → Action | Untrusted input changes agent behavior. | Blast radius extends to tool calls, memory writes, and sub-agent spawns rather than merely bad text. Assume injection occasionally succeeds; constrain what it can reach via capability narrowing + runtime monitoring. See ATLAS AML.T0051. |
| **Sensitive disclosure across channels** | Action / Delegation | Agent leaks data not only via its user-facing output but via tool inputs, sub-agent prompts, and memory writes. | Disclosure surfaces multiply beyond chat. Mitigation: classify data; redact at every egress surface (tool args, sub-agent prompts, memory); never assume "internal" channels are safe. |
| **Supply-chain compounding** | Action | A compromised model, library, or tool dependency means the agent's *actions* are compromised, not just its words. | Compounds beyond chat because the agent acts. Cross-ref Q2-3.2 `mcp-governance.md` for MCP-server supply-chain controls; verify tool integrity and dependency provenance. |
| **Improper self-handling of output** | Planning → Action | In an agent system the agent IS the downstream consumer of its own output, using it to drive tool calls. | Output-validation gates must sit **between plan and action**, not just between LLM and user. Validate the plan step before it executes a side effect. |
| **Excessive agency** | Action / Delegation | The agent holds more capability than the task requires (the agent-system form of over-broad-token). | Mitigation: Q2-3.1 §Capability Tokens narrowing on every delegation hop; grant the minimum capability per action; revoke on completion. |
| **Plan & system-prompt exposure** | Planning | The agent's system prompt encodes tool-routing logic, available capabilities, and trust boundaries; if extracted it is reconnaissance for Goal Manipulation and tool-use attacks. | Defense-in-depth: **assume the system prompt will leak** and ensure no security-relevant secret lives only in it; pair with runtime monitoring for plan deviation. Security controls live in the identity service / authorization layer, not in prompt text. |
| **Retrieval & embedding corruption** | Memory | Adversarial inputs corrupt RAG retrieval or embedding-space classification; vectors become memory anchors driving future tool calls, so poisoning one document yields long-tail influence. | Source-provenance on every embedded chunk, retrieval-side filtering, periodic re-indexing with provenance verification. Cross-ref ATLAS AML.T0080 Memory Poisoning. |
| **Unbounded consumption** | Action | Resource exhaustion via expensive operations — tool calls are billable, sub-agent spawns are billable, an unbounded agent loop is an unbounded bill. | Also a financial-DoS surface. Mitigation: per-run budgets, spawn-depth limits, loop detection, hard caps on billable tool calls. |

Cross-reference to MCP attack surfaces: Q2-5.1 `mcp-architecture.md` (Wave 2 sibling pack, pending stitching pass) covers transport-level attack surfaces — capability tokens on the wire, mTLS at transport, federation across MCP servers. The supply-chain-compounding and excessive-agency rows above will receive MCP-specific elaboration after the Wave 2 stitching pass per M40.

## 2026-06 Delta Update (as of 2026-06-06)

### "Comment-and-Control" — coding-agents-in-CI/CD prompt injection (disclosed 2026-04-15)

This is a named, in-the-wild attack class against the **exact pattern the OS itself endorses**: autonomous coding agents running inside GitHub Actions on pull-request / issue events. It is recorded here because the OS's own `subagent-driven-development.md` and `incident-response-dev.md` workflows put coding agents in CI/CD, so this attack maps directly onto the OS's recommended posture.

**Mechanism.** A single piece of attacker-controlled text — a **PR title, issue body, or comment** — is read into the agent's context when the CI agent processes the event. Because that text is untrusted input treated as trusted instruction, one crafted comment can simultaneously hijack **Claude Code Security Review, Gemini CLI Action, and GitHub Copilot Coding Agent** when they run in GitHub Actions. The injected instructions cause the agent to read repository secrets / API keys from its environment and exfiltrate them **back through GitHub itself** — the platform becomes the command-and-control (C2) channel (e.g., writing the secret into a comment, branch, commit, or workflow artifact the attacker can read), so the exfiltration rides legitimate GitHub traffic and evades egress controls that only watch for unknown destinations.

**Severity.** Anthropic rated the Claude Code finding **CVSS 9.4 (Critical)**. Broad industry coverage followed mid-May 2026.

**Where it maps in this pack.** This is a **Perception-surface** injection (untrusted PR/issue/comment text changing agent behavior) compounding into **Action-surface** sensitive disclosure (secret exfiltration) and **excessive agency** (the CI agent has secret-reading + GitHub-write capability it does not need for the task). In MITRE ATLAS v5.4 terms it is **AML.T0051 (LLM Prompt Injection)** escalating into agent tool-use (the agent uses its GitHub write tools as an exfiltration channel — cf. AML.T0053).

**Mitigations to capture (reviewer must verify all four):**
- Treat **ALL** PR / issue / comment text as untrusted input — never let event-supplied text reach the agent's instruction channel; isolate it as data, not instructions.
- **Least-privilege Action tokens** — CI agent tokens scoped to the minimum repo/permission set; no broad `secrets` exposure into the agent's environment.
- **No secrets in agent context** — secrets never injected into the prompt/environment the agent can read; use short-lived, scoped, masked credentials surfaced only to the build step that needs them, not the reasoning step.
- **Human approval gates on CI agent actions** — state-changing or external-write actions taken by a CI agent require a human approval gate, not auto-execution on event trigger.

### Related in-window agentic-security incidents (one-line mentions)

These landed in the same window and reinforce the same lesson — untrusted content reaching an agent's instruction/execution surface:
- **NousResearch Hermes Agent** — persistent prompt injection via **unscanned `DESCRIPTION.md` skill files** (skill metadata is untrusted content too).
- **Google Antigravity** — RCE / sandbox-escape via the **`find_by_name`** tool (tool-use reaching code execution).

## Agent-to-Agent Threat Model (per M34 — cites Q2-3.1 by name)

This section is load-bearing. The four agent-identity patterns named verbatim in **Q2-3.1 `agent-identity.md` §Agent-to-Agent Authentication** anchor the threat model below. Each pattern has a specific defensive profile; each pattern has corresponding attack vectors that defenders MUST cover. The threat model below is the inverse of the identity controls: every defense in Q2-3.1 maps to specific attacks here. It is the Delegation surface of the five-surface decomposition, treated in depth.

### Pattern 1 — Capability-Token Forwarding with Narrowing

*Q2-3.1 names this as the default pattern in Microsoft Entra Agent ID and Google Agent Identity. The defensive idea is that the sub-agent's token is a strict subset of the spawning agent's token, so the sub-agent cannot escalate.*

| Attack Vector | Description | Defensive Control |
|---|---|---|
| **Token theft mid-forwarding** | Adversary intercepts the capability token during the spawn-and-forward handshake (memory dump, side channel, log leakage, observability platform leakage). | Tokens never logged in plaintext; observability redacts; transport is mTLS-protected per Pattern 2; tokens are short-lived (minutes-to-hours per Q2-3.1 §Capability Tokens) so a stolen token expires before exploitation chains compound. |
| **Narrowing-rule bypass** | The narrowing logic is implemented at the application layer rather than cryptographically; an adversary who controls part of the application can issue tokens broader than the spawning agent's own scope. | Narrowing is enforced at the identity service / authorization server (the policy decision point), not by the spawning agent's process. Identity-service-issued tokens are signed; downstream verification rejects tokens whose claims exceed the spawning principal's authority. |
| **Token replay across agent boundaries** | A token issued for spawn A → sub-agent B is replayed by spawn A → sub-agent C (or by an adversary impersonating spawn A). | Tokens bind both spawning identity AND receiving identity (audience claim); receiving agent validates the audience matches its own identity before accepting. Reuse against a different audience fails validation. |

### Pattern 2 — Mutual TLS with Agent Certificates

*Q2-3.1 names this as the Cisco Agentic Zero Trust emphasis. Each agent holds a short-lived certificate identifying its agent-identity record; the receiving agent validates against the agent-identity service before accepting the call.*

| Attack Vector | Description | Defensive Control |
|---|---|---|
| **Certificate compromise** | Private key exfiltrated from agent runtime (key stored in memory dump, swap, container layer, snapshot). | Short certificate lifetime (matched to capability-token lifetime: minutes-to-hours, not days); ephemeral key material; key-rotation tooling treated as part of agent lifecycle (Q2-3.1 §Agent Lifecycle Management); attestation that the runtime holding the key is unmodified. |
| **Certificate-rotation gaps** | A rotation window during which a deactivated agent's certificate is still trusted because revocation has not propagated. | Revocation-by-default architecture: agents query the identity service per-call (or per-short-window cache); CRL-style "list of bad certs" is the fallback, not the primary mechanism. Q2-3.1 §Capability Tokens row "Revocation must be immediate and propagated" applies. |
| **Agent-card spoofing** | An adversary registers a malicious agent with a name or display-identity confusable with a legitimate one (e.g., zero-width spaces in display name, lookalike Unicode). Receiving agent validates the cert is signed by the agent-identity service but doesn't validate the *binding* between cert and intended agent. | Q2-3.1's §Anti-Patterns row 1 distinction applies operationally: receiving agent validates the **system identity** in the cert against an allowlist of expected callers, not the display name. This is MITRE ATLAS Masquerading (AML.T0074) at the agent-identity layer. |

### Pattern 3 — OAuth-Style Delegation with `act_as` Claim

*Q2-3.1 names this as the cross-tenant delegation pattern in Microsoft Entra Agent ID. The token names both principals: the spawning agent and the sub-agent, with the sub-agent acting on behalf of the spawning agent.*

| Attack Vector | Description | Defensive Control |
|---|---|---|
| **`act_as` escalation** | Sub-agent submits an `act_as` claim asserting a principal it does not actually represent (e.g., human user X) because policy evaluation at the identity service trusts a header rather than a verified delegation grant. | Identity service evaluates `act_as` against an explicit delegation grant on file; sub-agent cannot self-assert `act_as`. The grant is recorded at provisioning (Q2-3.1 §Agent Lifecycle Management row "Provisioning"). |
| **Claim manipulation** | Adversary modifies token claims in flight (audience, scope, expiry) because the token is not cryptographically integrity-protected end-to-end. | Tokens are signed by the identity service (JWT with asymmetric signature; receiving agent validates against the identity service's public key). Tampered tokens fail validation. |
| **Audience confusion** | Token issued for service A is presented to service B; service B accepts it because audience validation is loose. | Strict audience validation: token's `aud` claim must exactly match the receiving service's identifier; multi-audience tokens are rejected at sensitive consumers. This is the OAuth-style version of Pattern 1's "token replay across agent boundaries." |

### Pattern 4 — Workload Identity Federation Bridging

*Q2-3.1 names this as the cross-cloud pattern; Google Agent Identity is the reference implementation. The receiving environment exchanges a source-cloud token for a local token via federation.*

| Attack Vector | Description | Defensive Control |
|---|---|---|
| **Federation-token leakage** | Source-cloud token leaks during the federation exchange (logs, instrumentation, sidecar misconfiguration). | Federation exchange happens via the cloud's identity service, not through application code; tokens are never logged; observability redacts federation tokens explicitly. |
| **Cross-cloud impersonation** | Adversary in cloud A obtains a source-cloud token (via theft or insider compromise) and uses federation to escalate into cloud B. | Federation policy at cloud B restricts which source-cloud principals can federate; binding is per-principal, not blanket; deactivation in cloud A propagates to federation policy in cloud B via Q2-3.1 §Agent Lifecycle Management row "Deactivation." |
| **Audience-claim spoofing in federation exchange** | Source-cloud token's audience is manipulated during exchange so the receiving cloud issues a token broader than the source token's authority. | Federation policy validates source-token audience BEFORE issuing local token; mismatched audience fails the exchange. Cross-ref Pattern 3 "Audience confusion." |

### Cross-Pattern Defensive Synthesis

The four patterns are not alternatives — production systems usually use a combination. mTLS (Pattern 2) at the transport layer, capability-token forwarding (Pattern 1) for in-cloud delegation, OAuth-style delegation (Pattern 3) for cross-tenant, and Workload Identity Federation (Pattern 4) for cross-cloud. The threat model above must be evaluated **at each layer** the deployment uses, not pattern-by-pattern.

## Retrieval & Memory Corruption (Memory Surface, in depth)

The Memory surface deserves dedicated treatment because it is the one surface where a single adversarial action gains *long-tail* influence — a poisoned chunk re-injects on every future retrieval until it is evicted, which may not happen for months. This maps to MITRE ATLAS **AML.T0080 (Memory Poisoning)**.

- **Provenance on every write.** Every embedded chunk carries source metadata (origin, ingestion time, content-hash). A memory store without per-chunk provenance cannot answer "what poisoned this and when," which means it cannot be forensically reconstructed after an incident.
- **Retrieval-side filtering.** The query path can exclude untrusted-source chunks at retrieval time, so even a poisoned store does not feed untrusted content into the plan unless the policy explicitly admits that source.
- **Periodic re-indexing with provenance verification.** Wired into the agent lifecycle, not run ad hoc; re-verifies that the source of each chunk is still trusted and that the content-hash matches.
- **Memory-write audit.** Captures source + content-hash on write, so the blast radius of a poisoning event is bounded by what the audit can reconstruct.

Detection lags on this surface because the agent's output remains within content-policy norms — the bias is structural, not toxic — so provenance and audit are the detection mechanism, not output classifiers.

## AI-Assisted SAST in the Review Loop

The Comment-and-Control section above is the *attack* on the coding-agent-in-CI surface; this section is the *defensive layer* on the same surface. AI-assisted static analysis (Semgrep AI, Snyk AI) is a generation-time and PR-time scanning layer that produces a structured first pass of security findings on a diff — but the load-bearing V2V discipline is that **SAST-AI findings are triage input, not merge clearance**. A scanner that emits zero findings has not approved the merge; a human (or a Claude review pass) still gates it. This is the same input-to-review framing the whole pack operates under: the scanner drafts and triages, the reviewer owns.

### Where the two tools sit

| Tool | Scans | Where it runs | What it adds over a plain linter |
|---|---|---|---|
| **Semgrep / Semgrep AI** | First-party source code (taint flows, injection sinks, secret patterns, insecure-API usage) | Generation-time (editor/agent inline) + PR-time (CI check) | AI-authored custom security rules tuned to the repo's own patterns; AI-suggested autofix on findings; cross-function taint tracking beyond regex linting |
| **Snyk / Snyk AI** | First-party code (Snyk Code) **+ dependencies (Snyk Open Source / SCA) + IaC (Snyk IaC)** | Generation-time + PR-time | Known-CVE dependency graph, transitive-dep reachability, IaC misconfiguration checks, AI-prioritized fix PRs |

The two are complementary, not redundant: Semgrep is strongest on bespoke source-pattern rules over *your* code; Snyk adds the supply-chain (CVE/SCA) and infrastructure-as-code surfaces — which maps directly onto this pack's **supply-chain-compounding** failure mode, where a compromised dependency means the agent's *actions* are compromised. Run both as the security-sensitive-diff scanning layer; neither alone covers source + deps + IaC.

### The discipline — findings are triage input, not merge clearance

This is the non-negotiable. SAST-AI is folded into the review loop as a **finding generator that feeds the gate**, never as the gate itself:

- **A clean scan is not an approval.** Static analysis has false negatives (novel sinks, business-logic flaws, auth-model errors no rule encodes). Zero findings means "no *known-pattern* issue surfaced," not "safe to merge." The human/Claude review pass still runs and still gates.
- **A finding is a prompt to review, not an auto-block by itself, and an autofix is a suggestion, not a commit.** Semgrep AI autofix and Snyk fix-PRs are *proposed* diffs; they enter the same review gate as any other change. An AI-suggested fix that "resolves" a finding can introduce a different defect or paper over the real one — the reviewer reads the fix, not just the green check.
- **Security-sensitive diffs get the scan + a human-judgment pass.** This is the defensive inverse of Comment-and-Control: that attack rides untrusted PR text into the agent's instruction channel; here, the SAST layer is a *control on the diff*, but it must not become the autonomous approver of its own analysis — that would re-create the "filter fails open into autonomous action" failure (Finding 1). The control is layered: scanner findings + reviewer judgment, both required.

### SARIF ingestion + false-positive triage posture

- **SARIF is the interchange.** Both Semgrep and Snyk emit OASIS SARIF v2.1.0. Ingest SARIF into the PR surface (e.g., GitHub code-scanning) so findings annotate the exact lines in the diff and persist across re-runs — rather than living in scattered tool logs the reviewer has to reconcile. SARIF gives the reviewer one normalized finding stream regardless of which scanner produced it.
- **False positives are triaged, not silently suppressed.** SAST-AI on real codebases produces noise. The posture: a suppressed/accepted finding carries a recorded rationale (inline suppression comment or tracked ignore with reason + owner), so a later reviewer can see *why* it was dismissed — the same provenance discipline this pack applies to memory writes. Blanket disabling of a rule is a decision, not a default; it gets a one-line justification, ideally an ADR reference for repo-wide rule changes.
- **Tune rules toward the repo's real threat surface.** Semgrep AI custom rules should target this codebase's actual sinks (its auth model, its tool-invocation boundaries, its secret-handling), not a generic ruleset that drowns the reviewer. High-noise rules erode the gate by training reviewers to rubber-stamp.

## NIST CAISI Reference Architecture Alignment

NIST's CAISI AI Agent Standards Initiative (Feb 2026), companion to the NIST AI RMF, publishes a reference architecture for agent systems with explicit attack-surface partitioning. Both are U.S. Government work in the public domain; V2V draws concepts and structure, not third-party-credited figures. V2V's posture:

- **Where V2V aligns with CAISI**: the partitioning of (a) agent runtime, (b) tool execution, (c) memory store, (d) identity service into distinct trust zones with explicit cross-zone control points. Each zone has its own threat model; the cross-zone interface is the highest-leverage defensive surface. This aligns cleanly with V2V's five-surface decomposition above.

- **Where V2V diverges from CAISI**: V2V maintains an explicit **identity-vs-display-identity distinction** per Q2-3.1 `agent-identity.md` §Anti-Patterns row 1 and §Implementation Guidance #3. The V2V Identity Registry (per `.claude/rules/agent-spawn-protocol.md` §1) is in-conversation display only (emoji, display name, RACI surface) and is runtime-only with no system-level trust grant. The system identity is a separate concern governed by the agent-identity service. CAISI's reference architecture does not name this distinction explicitly; V2V's view is that conflating the two surfaces — i.e., treating the conversation-level display identity as a credentialed principal — is an anti-pattern that produces either leak (display surface acquires credential semantics) or loss (credential surface lacks proper governance because the display surface was treated as authoritative).

The integration point with `/ai-control-audit` skill invocation: an `/ai-control-audit` run targeting an agent system MUST evaluate the deployment against (a) the four Q2-3.1 identity patterns, (b) the MITRE ATLAS v5.4 agent-specific technique coverage, and (c) the seven V2V agent-specific failure modes across the five surfaces. Findings from all three feed the audit's structured first-pass output for reviewer triage.

## Findings

### Finding 1
**What**: Deployments adopting agent systems in 2026 frequently treat prompt-injection (MITRE AML.T0051) as a separate concern from agent-action security, addressing it via input-filtering or output-classifier controls without addressing the action-layer blast radius. NIST CAISI's 81% red-team attack-success rate against agents is partly explained by this gap: filters fail open into autonomous action.
**Why it matters**: A prompt-injection that is "merely" a content-policy violation in an LLM-as-chat system becomes a tool-execution event, a sub-agent spawn, a memory write, or an external-system side-effect in an agent system. Input filtering reduces injection success rate but does not bound blast radius when filtering is bypassed. The architecture must assume injection succeeds occasionally and constrain what successful injection can DO — which is the identity-and-capability-narrowing layer (Q2-3.1) plus runtime monitoring.
**Severity**: **P0**
**Suggested next step**: Reviewer verifies the deployment has (a) Q2-3.1 capability-token narrowing on every delegation hop, (b) per-action approval gates for high-impact tools (financial actions, customer-facing communications, data-exfiltration-capable tools), and (c) runtime monitoring for plan-vs-action deviation — not solely input filtering or output classifiers. Engage `security-architect` and `ai-architect` jointly.

### Finding 2
**What**: Multi-agent architectures frequently assume agent-to-agent authentication is "handled" by the identity service without verifying that ONE of the four Q2-3.1 patterns (capability-token forwarding with narrowing / mTLS with agent certificates / OAuth-style delegation with `act_as` / Workload Identity Federation) is actually deployed at every agent-to-agent call boundary. The deployment often runs on implicit network trust (same VPC = trusted), which means an attacker with foothold in any agent in the VPC can impersonate any other.
**Why it matters**: MITRE ATLAS Inter-Agent Spoofing / Masquerading (AML.T0074) maps directly here. Without a named Q2-3.1 pattern at the agent-to-agent boundary, none of the §Agent-to-Agent Threat Model controls above are in place: there is nothing to detect token theft, nothing to enforce narrowing, nothing to prevent `act_as` escalation, nothing to prevent cross-cloud impersonation.
**Severity**: **P0**
**Suggested next step**: Reviewer maps each agent-to-agent call boundary in the deployment to a named Q2-3.1 pattern, documents the binding, and verifies the defensive controls from §Agent-to-Agent Threat Model above are in place at each boundary. Engage `security-architect` and `chief-architect` jointly; escalate to `general-counsel` if EU deployment exists, because EU AI Act Article 15 robustness obligations attach.

### Finding 3
**What**: RAG-and-memory agent deployments often lack provenance tracking on memory writes and retrieved content (the retrieval-and-embedding-corruption failure mode; MITRE ATLAS Memory Poisoning AML.T0080, new agent technique). Embedded chunks are treated as if their source is implicit in the embedding; an adversary who corrupts one document chunk gains long-tail influence over downstream agent behavior, often with no audit signal that "memory was poisoned at time T from source S."
**Why it matters**: Long-running agent memory amplifies single-injection blast radius across many subsequent runs, against multiple users, until the corrupted vector is evicted (which may not happen for months). This is the agent-system version of supply-chain compromise: a compromised data source compromises agent behavior at every retrieval. Detection lags because the agent's output remains within content-policy norms; the bias is structural, not toxic.
**Severity**: **P1**
**Suggested next step**: Reviewer verifies (a) every embedded chunk carries source-provenance metadata, (b) retrieval-side filtering can exclude untrusted-source chunks at query time, (c) periodic re-indexing with provenance verification is wired into the agent lifecycle, and (d) memory-write audit captures source + content-hash for forensic reconstruction. Engage `data-architect`, `security-architect`, and `ai-architect`.

## Anti-Patterns / Common Failures

| Anti-Pattern | Why It Fails | What V2V Does Instead |
|---|---|---|
| **Prompt-injection treated as separate from agent-action security** | Input filtering reduces injection rate but does not bound action-layer blast radius when filtering is bypassed; the architecture fails open into autonomous action. | Assume injection occasionally succeeds; constrain capability via Q2-3.1 narrowing; runtime-monitor plan-vs-action deviation; per-action approval gates on high-impact tools. |
| **Identity layer assumed when not actually deployed** | Implicit network trust ("same VPC = trusted") is treated as an identity control; an attacker with foothold in any agent impersonates any other. | Every agent-to-agent call boundary maps to a named Q2-3.1 pattern; mapping is documented and verified, not assumed. |
| **Threat model ignores Q2-3.1 §Agent-to-Agent Authentication patterns** | Threat model written in terms of "the agent" without naming the identity primitive means defenses are also unnamed, which means defenses are also unverified. | §Agent-to-Agent Threat Model above is structured by the four Q2-3.1 patterns; each pattern's attack vectors are enumerated; reviewer maps deployment to pattern. |
| **Over-reliance on input filtering without runtime monitoring** | Input filter is a static control against an adaptive adversary; once bypassed, no detection of subsequent agent behavior. | Defense-in-depth: input filter + capability narrowing + runtime monitoring for plan-vs-action deviation + post-hoc audit. Single-layer control is insufficient. |
| **System prompt treated as a secret** | Plan-and-system-prompt exposure: system prompts leak; defense plans that rely on prompt secrecy collapse on first leak. | Assume system prompt leaks; ensure no security-relevant secret lives only in it; security controls live in identity service / authorization layer / runtime monitoring, not in prompt text. |
| **RAG / memory writes with no provenance** | Memory poisoning (ATLAS AML.T0080) gains long-tail influence with no detection signal; structural bias is hard to detect post-hoc. | Source-provenance on every embedded chunk; retrieval-side filtering; periodic re-indexing with provenance verification; memory-write audit captures source + content-hash. |
| **Conversation-level display identity treated as credentialed principal** | Per Q2-3.1 §Anti-Patterns row 1: V2V Identity Registry is in-conversation display only, runtime-only; treating it as a credentialed principal means either the display surface acquires credential semantics or the credential surface lacks proper governance. | Maintain both surfaces with documented binding; Identity Registry stays runtime-only; system identity stays in the identity service. |
